# 技术方案规范

> 适用于 `design_tech_solution`（产出方案）与 `implement_code`（按方案落地）。
> 定位：给用户做**全局把控**的短文档，不是设计说明书。核心是 **DDL** 与 **领域命名**，实现只讲方向。

## 底线要求

1. 写代码前必须先出技术方案；方案未 `tech_design_approval: approved` 不得进入实现。
2. **人工模式下必须由用户确认**，AI 不得自行 approved。
3. 正文（不含 DDL 代码块）**150 行以内**，宁短勿长。
4. 只讲方向，不写文件清单、类名方法签名、逐行实现步骤。

## 必含章节

| 章节 | 要求 |
|------|------|
| 背景与目标 | 做什么 2-3 句 + 非目标 1-3 条 |
| 领域模型与术语 | **术语清单**（术语 / 英文命名 / 定义 / 与现有概念的关系，≤15 条）+ `classDiagram` 领域模型图及说明 |
| 数据结构及说明 | **完整可执行 DDL** + 字段说明表；不涉及库表写「不涉及」并说明数据落在哪 |
| 实现方向 | 分几步、谁调谁、用什么模型或设计模式（落哪一层）、关键取舍；不写细节 |
| 关键接口 | 方法 / 路径 / 用途 / 入参要点 / 出参要点；无接口写「不涉及」 |
| 兼容性与风险 | 最多 3 条 |
| 人工后续事项 | 需人工执行的 DDL / 配置 / 权限；没有写「无」 |

## 领域命名约定

- 中英文**一一对应**：术语清单的「英文命名」即表名 / 字段名 / 类名 / 接口名，同一概念不许多种叫法。
- 新造名词必须先定义再使用；沿用现有代码里的叫法，不要另起一套。
- 领域模型用 `classDiagram`，只画聚合根与关键实体、值对象及其关系，不画全部字段。

## DDL 约定

- 用项目现有数据库方言，字段风格对齐现有表。
- 必须含：主键、必要索引与唯一约束、字段注释、表注释、字符集/引擎（MySQL）。
- 变更类需求给 `ALTER TABLE`，并说明存量数据如何回填。
- **禁止**「字段同上」「略」「按需添加」这类占位表述。
- DDL 只写进文档，**不连库执行**；执行动作写入「人工后续事项」。

## 图与格式

- mermaid 必须自检：引号成对、括号闭合、节点名用业务语言。
- 图后必须有文字说明，不能只有图。

## 与代码实现的关系

- `implement_code` 以方案的领域命名、表结构、接口为准；实现与方案不一致时，先问用户或回写方案。
