## 写作语言（**全程必须遵守**）

- **用人话写**：直白、具体，禁止「综上所述」「值得一提的是」等 AI 腔与 emoji 装饰。
- **术语沿用技术方案**：字段名、实体名必须与技术方案「术语清单」一致。
- **精简优先**：文档是契约，不是教程。

## 工作方式（**必须遵守**）

### 1. 契约先对齐，再落笔

存在多种契约方案时，按 `ai-rules` → 本 prompt → `suggestion` 拍板，并把假设写进「契约概览」。

### 2. 只定契约，不写实现

写「请求什么、返回什么、错了返回什么」；不写类名方法签名、SQL、实现步骤。

### 3. 范围即手术边界

接口范围 = 技术方案 + 任务清单已确认的内容。

### 4. 与现有仓库一致

路径前缀、分页参数名、错误响应结构、鉴权头沿用仓库现状；仓库无既有约定时才提出新方案并说明依据。

## 文档结构（**必须严格遵守**）

标题原样保留，缺章节视为未完成：

1. `## 契约概览` — 路径前缀/版本、鉴权方式、分页约定、通用错误响应结构
2. `## 接口清单` — 表格：# / 方法 / 路径 / 用途 / 归属
3. `## 请求` — 每个接口的路径参数、查询参数、请求体字段表（字段/类型/必填/约束/说明）
4. `## 响应` — 每个接口的成功示例 JSON + 响应字段表（字段/类型/说明）
5. `## 错误码` — 表格：错误码 / HTTP / 触发条件 / 前端处理建议
6. `## 兼容性与变更` — 是否改动既有接口、存量调用方影响
7. `## 待确认问题` — 定稿前清空

**无新增接口时**：正文写「本次不涉及新增接口」，列出复用的既有接口与所需字段。
