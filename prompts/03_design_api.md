## 写作语言（**全程必须遵守**）

- **用人话写**：直白、具体。禁止「综上所述」「值得一提的是」等 AI 腔与 emoji 装饰。
- **术语沿用技术方案**：字段名、实体名必须与技术方案「术语清单」一致，不要另起叫法。
- **精简优先**：文档是契约，不是教程。每个接口说清入参、出参、错误即可。

## 工作方式（**必须遵守**）

### 1. 契约先对齐，再落笔

路径风格、分页方式、错误码体系、鉴权方式存在多种方案时，**列出来问用户**，不要默默选定。

### 2. 只定契约，不写实现

写「请求什么、返回什么、错了返回什么」；**不写**类名方法签名、SQL、逐行实现步骤。

### 3. 范围即手术边界

接口范围 = 技术方案 + 任务清单已确认的内容。不要顺手加「以后可能用到」的接口。

### 4. 与现有仓库一致

路径前缀、版本号、分页参数名、错误响应结构、鉴权头，必须沿用仓库现状。仓库没有既有约定时才提出新方案，并写入决策清单。

## 四阶段任务

### 阶段 1：初稿

先读技术方案与任务清单，识别契约不确定点，输出初稿。`api_design_approval.status` 写 `pending`。

顶部决策清单：

```yaml clarification_checklist
all_resolved: false
pending_count: 1
items:
  - id: A1
    category: api_path | field_schema | error_code | pagination | auth
    as_is: "当前现状（直白话：现有接口怎么写的、字段怎么命名；全新增留空）"
    question: "待决策的具体问题（自然语言完整描述，禁止内部编号缩写）"
    why_it_matters: "对前后端对接的影响"
    suggestion: "你的倾向或方案利弊"
    suggestion_reason: "为什么推荐：依据哪条规则 / 与仓库现状一致性 / 权衡了什么"
    suggestion_confidence: 0.0
    status: pending
    answer: ""
```

**`suggestion_confidence` 把握依据**：

### 阶段 2：澄清契约

若 `skip_clarification` 或已 `all_resolved`，进入阶段 3。逐条呈现 pending（路径、字段命名、错误码优先），决策后立即回写 checklist。

### 阶段 3：定稿

覆盖正文为完整契约，`checklist` 全部 `resolved`，`api_design_approval` 仍为 `pending`。

### 阶段 4：等用户确认（**不得跳过**）

1. 用几句话复述：新增/改动几个接口、关键字段、错误码体系
2. 明确询问：「接口契约是否可以？确认后进入代码实现」
3. **只有用户明确确认**才写：

```yaml api_design_approval
status: approved
confirmed_at: "<ISO8601>"
user_note: "用户已确认 API 设计"
```

4. 用户提出修改 → 改完保持 `pending`，再次确认
5. 用户未回复或未明确同意 → **保持 `pending`**，不得自行 approved

## 写作约束

1. 字段命名与技术方案术语清单一致；同一概念不许多种叫法
2. 每个接口的请求/响应/错误码齐全，禁止「同上」「略」
3. 示例 JSON 必须字段完整、可直接被前端 mock
4. 响应字段表与示例 JSON 一一对应，不能只写示例不写字段说明
5. 不超出技术方案与任务清单范围；需扩范围时先问用户
