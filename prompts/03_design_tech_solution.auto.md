**本节点不写业务代码**，只产出技术方案文档。读者是开发同学，目标是让他们看清方向。

## 写作语言（**全程必须遵守**）

- **用人话写**：直白、具体，禁止「综上所述」「值得一提的是」等 AI 腔与 emoji 装饰。
- **术语必须定义**：业务黑话、专业名词、自造概念一律进「术语清单」，给出与代码一致的英文命名。
- **精简优先**：给用户做全局把控的文档，能一句话说清就不写一段。

## 工作方式（**必须遵守**）

### 1. 先想清再落笔

存在多种方案时，按 `ai-rules` → 本 prompt → `suggestion` 拍板，把假设写进「实现方向」的取舍部分。

### 2. 只讲方向，不抠实现

写「用什么模型 / 分几层 / 谁调谁 / 为什么这么选」；不写文件清单、类名方法签名、逐行步骤。表结构与领域命名例外，必须精确到字段级。

### 3. 范围即手术边界

方案范围 = 需求 + plan + review + 任务清单。

### 4. 与仓库现状一致

表命名、分层、依赖对齐现有代码；需改既有公共能力时选新增路径并说明原因。

### 5. 按本次角色设计（**必须遵守**）

{{role_scope}}

- 只有「后端」→ 只设计后端
- 只有「前端」→ 只设计前端，不设计库表
- 「后端、前端」→ 两块都设计并标注归属
- 「未识别」→ 按任务清单归属判断；仍无法判断时取覆盖面更小的方案并写明依据

## 文档结构（**必须严格遵守**）

标题原样保留，缺章节视为未完成：

1. `## 背景与目标` — 做什么（2-3 句）、不做什么（非目标 1-3 条）
2. `## 领域模型与术语`
   - `### 术语清单` — 表格：术语 / 英文命名 / 定义 / 与现有概念的关系（≤15 条）
   - `### 领域模型` — ```mermaid classDiagram``` + 3-5 句说明聚合边界、实体关系、状态流转
3. `## 数据结构及说明` — **完整可执行 DDL**（主键/索引/唯一约束/注释齐全）+ 字段说明表；不涉及库表写「本次不涉及数据库变更」并说明数据落在哪
4. `## 实现方向` — 分几步/谁调谁（3-6 条）、采用的模型或设计模式及落层、关键取舍（1-3 条）；不写文件清单与方法级细节
5. `## 关键接口` — 方法/路径/用途/入参要点/出参要点；无接口写「不涉及」
6. `## 兼容性与风险` — 最多 3 条
7. `## 人工后续事项` — 需人工执行的 DDL/配置/权限；没有写「无」

## 篇幅约束（**必须遵守**）

- 正文（不含 DDL 代码块）**150 行以内**，宁短勿长
- 术语清单 **≤ 15 条**，只收本次真正用到的
- 每小节 2-5 句；不写「改动清单」「异常码大全」「压测方案」等实现期细节

## 自决流程

1. 识别不确定点，写入顶部 `clarification_checklist`（含 `suggestion` / `suggestion_reason` / `suggestion_confidence`）
2. 按阈值 `{{recommendation_threshold}}` 自行采纳，全部标 `resolved` 并写 `answer`
3. 按「先术语与领域模型 → 再 DDL → 最后实现方向」的顺序定稿
4. 写入自动审批：
